# Hapticpad v2.1 Low Latency

## Цель

Сократить постоянную задержку каждой буквы и устранить редкие задержки в сотни миллисекунд, возникавшие при одновременной работе макросов, GUI и клавиатуры.

## Изменения firmware

| Параметр | v2.0 | v2.1 |
|---|---:|---:|
| Debounce нажатия | 8 мс | 2,5 мс |
| Debounce отпускания | 8 мс | 4,5 мс |
| Период scan | около 1 мс | 250 мкс |
| GPIO read | 26 × `digitalRead()` | один `gpio_get_all()` на RP2040 |
| Host commands | весь доступный буфер до scan | максимум 16 байт после scan |
| Firmware version | `2.0.0` | `2.1.0-lowlatency` |

Параметры можно переопределить при сборке:

```ini
build_flags =
    -DHAPTICPAD_PRESS_DEBOUNCE_US=3000
    -DHAPTICPAD_RELEASE_DEBOUNCE_US=5000
    -DHAPTICPAD_SCAN_PERIOD_US=250
```

Для неизвестных механических переключателей рекомендуется начать с профиля 3/5 мс и уменьшать press debounce только после осциллографического или логического измерения дребезга.

## Изменения companion app

Старый путь имел один worker:

```text
text → macro step → sleep 50 ms → command → next text
```

Новый путь:

```text
Physical stroke → realtime queue → input worker → SendInput

Macro/command → background queue → scheduler
                              └→ low-priority macro step queue
```

Свойства:

- физические strokes не ждут `sleep` макроса;
- комбинация исполняется атомарно одним input worker;
- realtime queue не удаляет символы при переполнении;
- background queue может сбросить лишний макрос вместо блокировки последующего текста;
- задержка шага макроса уменьшена с 50 до 12 мс;
- `SendInput` получает down/up одним массивом;
- обычное успешное нажатие не пишет синхронный log;
- выделенный Windows input worker закрепляется за OS thread и получает `THREAD_PRIORITY_ABOVE_NORMAL`.

## Результат нативной проверки

```text
PASS: firmware state machine; press_latency_us=2750; backlog_press_latency_us=2750
```

Измерение производится на настоящем `src/MacroPad.ino` с эмуляцией Arduino GPIO, `micros()` и USB Serial API.

Это подтверждает:

1. stroke формируется за 2,75 мс от изменения контакта;
2. большая входящая очередь host-команд не увеличивает эту задержку;
3. функциональная логика dual-role, языков, Rare, Shift, Number и Backspace остаётся корректной.

## Вычислительный путь resolver

После предварительного построения таблиц обычное разрешение semantic stroke не выделяет память:

```text
ResolveStroke base:       ~5.8 ns/op, 0 B/op, 0 allocs/op
ResolveStroke Shift+Rare: ~5.9 ns/op, 0 B/op, 0 allocs/op
ResolveTap:               ~2.0 ns/op, 0 B/op, 0 allocs/op
```

Это микробенчмарк Linux/AMD64, а не end-to-end измерение Windows. Его назначение — подтвердить отсутствие алгоритмического узкого места и heap/GC нагрузки на каждом символе.

## Ожидаемая end-to-end задержка

Без аппаратного стенда точное значение не заявляется. После изменений разумная инженерная цель:

| Точка | Ожидаемый диапазон |
|---|---:|
| Контакт → protocol stroke | 2,5–3,0 мс |
| Контакт → `SendInput` при свободной системе | примерно 4–9 мс |
| p95 до `SendInput` | менее 12 мс |
| Добавка от спящего макроса | 0 мс |

Время появления символа на экране дополнительно зависит от частоты обновления монитора и цикла перерисовки приложения.

## Что ещё может ускорить систему

Следующий крупный этап — composite USB:

- Raw HID interrupt endpoint 1 кГц для realtime stroke;
- CDC только для настройки и диагностики;
- фиксированный бинарный report вместо ASCII строки.

Он может уменьшить транспортный jitter, но требует изменения USB descriptor, firmware transport и Windows reader. В v2.1 он намеренно не включён без сборки и проверки на реальном Pico.

## Обязательная аппаратная валидация

Перед снижением press debounce ниже 2,5 мс:

1. измерить 1000 нажатий каждой модели кнопки;
2. определить p99 длительности дребезга;
3. добавить запас не менее 0,5 мс;
4. выполнить 100 000 автоматических циклов;
5. убедиться в отсутствии двойных символов и ложных модификаторов.
